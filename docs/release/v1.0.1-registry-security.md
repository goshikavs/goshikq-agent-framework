## Workflow controls

`publish-python.yml` and `publish-npm.yml`:

- Trigger is `workflow_dispatch` only. Pull requests and branch pushes do not run them.
- The job runs only when the input is exactly `PUBLISH`.
- Checkout ref is `refs/tags/<input>`, so a branch name is not a valid ref.
- `HEAD` must equal that tag, and that commit must be an ancestor of `origin/main`.
- The tag must be `v1.0.*` with patch `>= 1`, and it must match the package version in the tree.
- The job builds from that checkout. It does not download a package built by another workflow.
- Python hashes are printed before upload. `skip-existing` is false, and a PyPI 200 for that version aborts the job. The action is pinned to commit `7245906fb61fa33a13554f9d5fb856fe61758086` (v1.14.3, Twine 7.0.0) with PEP 740 attestations. v1.12.4 rejected Core Metadata 2.5.
- npm publish uses Node.js 24.22.3, which bundles npm 11.19.1. Trusted publishing requires npm 11.5.1 or newer and Node.js 22.14 or newer. The job runs `npm publish --access public --provenance` and aborts when `npm view` finds the version. A non-404 lookup failure also aborts.
- Permissions are `contents: read` plus `id-token: write` on the publish job. No registry token is stored in the repository.
- Each job names a GitHub environment (`pypi` or `npm`). Those environments do not exist until the owner creates them, so a dispatch fails closed.
