## 5. Durability and recovery

`python -m pytest tests/crash/test_crash_boundaries.py tests/evidence/test_evidence_scenarios.py`: **11 passed in 57.17s**.

Conditions: same host and debug binary; embedded Postgres data dir `target/test-pg/durable-rerun`; `GOSHIKQ_EMBEDDED_PG_PORT=55441`. Theseus binaries came from `target/test-pg/shared/install`. Per-barrier recovery latency was not instrumented. The only measured time is the suite wall clock above.

Covered by those tests: crash at five dispatch barriers, approval still pending across kill/restart, SSE reconnect, never-settles stays acknowledged and not `VERIFIED`, policy-change invalidation, retail return change blocks the refund. On Windows the embedded postmaster often survives the server kill; the harness attaches the restarted server to that already-listening database instead of launching a second postmaster.

Not measured here: database process kill as its own case, concurrent recovery workers, cancellation propagation timing, parent/child recovery timing, network timeout injection, lost acknowledgement after a successful external write beyond the crash barriers.

Exactly-once is not claimed. Without an idempotency key honored by the external API, a lost acknowledgement after a successful write needs operator reconciliation. See `docs/architecture/durable-recovery.md`.

- A workflow can `COMPLETED` without `VERIFIED`.
- Exactly-once external side effects are not guaranteed. Idempotency keys are required for safe retry. Otherwise reconcile.
- Prompt injection is not solved. A tool result cannot by itself verify a goal.
- `chrono`, `paste`, and `pin-utils` are unmaintained warnings.
- Windows ARM64 is experimental.
- Hosted IdP products were not interoperability-tested.
- The Python and TypeScript packages are not on public registries.
- `GOSHIKQ_AUTH_MODE=none` is for local development and these tests.
